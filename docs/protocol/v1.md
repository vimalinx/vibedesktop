# Desktop protocol v1

Protocol version **1.1** is independent of the application release version. The built-in desktop now consumes the same public SDK available to a separate frontend. React components do not own HTTP paths or daemon credentials.

## Boundaries

```text
Built-in desktop / independent desktop frontend
                    |
             public v1 SDK
                    |
        same-origin /api/v1 HTTP
                    |
         Vibe Desktop server adapter
                    |
       desktop storage / catalog / vibed
```

- `src/protocol/v1/index.ts` is the public TypeScript SDK entry. Its dependency graph uses relative imports and Web APIs only. Copy the v1 directory into a frontend using a TypeScript bundler; it does not require Next.js, React, the default components, or server modules. It is not yet a separately published npm package.
- `src/protocol/v1/types.ts` defines wire data. `data-source.ts` defines client input/output types. `operations.ts` defines HTTP methods, paths, response envelopes, and capability IDs. `compatibility-v1.json` records the initial operation inventory for regression tests.
- `src/lib/protocol-server` adapts the protocol to the existing business handlers. Old `/api/...` routes remain available for existing clients; new frontends should use `/api/v1`.
- `src/lib/desktop-data` is the built-in UI's compatibility facade over the SDK. Window geometry/session types live separately in `src/protocol/shell/v1.ts`; their storage and rendering are frontend concerns.
- Browser-native packages now own the desktop layout and interactions. Windows 11 and macOS ship through the same versioned shell host used by imported HTML/CSS/JS bundles. See [desktop packages](desktop-packages.md) for the loader, author API, effects, and trust boundary. The service protocol remains separate from the shell API.

Minor 1.1 adds project import to the `localApps.manage` capability: `localApps.importPlan` (read-only detection preview), `localApps.import` (generate the auditable `run.sh` bundle, register it, and with `start: true` verify health or roll back), and `localApps.bundle` under `localApps` (the generated manifest and script, or `null` for apps not imported from a project).

## Discovery and compatibility policy

`GET /api/v1` returns `protocol`, `version: { major, minor }`, `capabilities`, `operations`, `transport`, and `limits`. Discovery is the only endpoint outside the operation inventory. Every response, including errors, carries `x-vibe-protocol: 1.1`, a server-generated `x-request-id`, and `Cache-Control: no-store`.

The policy for v1 development and future releases is:

1. Preserve existing v1 operation IDs, paths, methods, required fields, and their meanings. Add optional fields, operations, or capabilities with a minor version increase. Consumers ignore unknown response fields. New enum values require consumer tolerance or a new opt-in capability; do not silently expand closed enums.
2. Put incompatible changes in `/api/v2`, with an explicit migration document. Do not silently repurpose or remove v1 routes. No v1 retirement date is scheduled; any future retirement requires an announced migration and overlap period.
3. A package declares an exact protocol major, a minimum minor, required capabilities, and optional capabilities. Missing required capabilities or the wrong major prevent activation; optional capabilities may be omitted. Capability discovery means the API is implemented, not that a daemon is currently reachable or an update is available.
4. Existing field and behavioral compatibility remains a review responsibility. The inventory regression test catches route/envelope changes; it is not a complete formal proof of semantic compatibility. The SDK checks the protocol stamp, required top-level keys, and collection shapes, not every nested property at runtime.

The built-in UI checks discovery before loading the desktop. An incompatible response shows a retry/error screen instead of hanging indefinitely.

## Calling the service

```ts
import { createDesktopClient, packageCompatibility } from './protocol/v1';

const desktop = createDesktopClient(); // /api/v1 on the current origin
const host = await desktop.describe();
const support = packageCompatibility(manifest, host);
if (!support.compatible) throw new Error('Unsupported desktop service');
const state = await desktop.loadDesktop();
```

`operations.ts` is the complete callable inventory. Paths are relative to the discovery base; `:id` is one opaque path segment. Use the SDK's methods rather than assembling paths. A local reverse proxy mounted at `/desktop` can use `createDesktopClient({ basePath: '/desktop/api/v1' })`; the proxy must route that prefix to the service. The discovery `basePath` is the canonical unprefixed mount. Absolute/remote SDK base URLs are rejected. Non-browser consumers may inject a fetch adapter, as demonstrated in the live protocol tests.

All mutations require an exact same-origin `Origin` or `Referer` header. The existing `VIBE_PUBLIC_ORIGIN` setting determines the browser-facing origin behind a proxy. This remains a local, single-user service; the v1 protocol introduces neither a remote authentication system nor a CORS API. Daemon tokens stay in the server process. Setup scripts and daemon-internal maintenance routes are not part of the v1 desktop interface.

Requests with a body use `application/json`. The maximum request body is 8 MiB of UTF-8, including backups. Invalid JSON, media type, input types, and excessive bodies are rejected before business handlers. Existing domain validation still applies. Unknown input fields are ignored, so do not rely on storing arbitrary fields through `updateDesktop`.

## Errors and interrupted mutations

```json
{
  "error": {
    "code": "revision_conflict",
    "message": "Preferences changed. Read the current revision before saving again.",
    "requestId": "server-generated-id",
    "retryable": false,
    "outcome": "unknown"
  }
}
```

The SDK raises `DesktopDataError` with `code`, `status`, `serverMessage`, `requestId`, `retryable`, and `outcome`. Client-side failures use `network_error`, `request_aborted`, `protocol_mismatch`, or `invalid_response`. Invalid client resource IDs fail with `invalid_request` and `outcome: not_started` before sending a request.

`not_started` means the boundary rejected the request before dispatch. `unknown` conservatively means a mutation may have reached a handler; it does not claim that a change occurred. After a handler is entered, even a domain rejection may carry `unknown`. Request IDs correlate a captured response; they are not idempotency keys or a persistent audit log.

There is **no automatic mutation retry**, including install, uninstall, app control, restore, or version management. An interrupted mutation may already have completed. Read current state before deciding what to do next. A `retryable` hint on a failed read does not cause the SDK to retry automatically. Selected polling reads share a 750 ms per-client cache; mutation attempts invalidate it. The default request timeout is 20 seconds and can be configured. Long-running work such as installation returns status to be polled.

## Desktop packages and preferences

`examples/desktop-package/manifest.json` shows metadata format `vibedesktop-package`, `manifestVersion: 1`. IDs are reverse-domain namespaces such as `org.example.classic-desktop`. Package versions and preference schema versions belong to the package author; they are separate from the service protocol version.

The manifest describes compatibility only. It grants no permissions and does not load JavaScript. A same-origin custom frontend has the authority of the user. Namespaces isolate stored configuration, not security principals. The bundle loader requires explicit trust before importing executable code; it is not an untrusted-code sandbox. See [the execution boundary](desktop-packages.md#configuration-trust-and-backups).

```ts
const id = 'org.example.classic-desktop';
const current = await desktop.packagePreferences.read(id);
const saved = await desktop.packagePreferences.replace(id, {
  ifRevision: current.revision,
  schemaVersion: 1,
  values: { dockPosition: 'bottom', iconSize: 48 }
});
```

- A missing namespace returns `{ revision: null, schemaVersion: 1, values: {} }`.
- Replacement requires the latest opaque `ifRevision`, including explicit `null` for creation. Concurrent writes to the same revision produce exactly one success and a `409 revision_conflict` for the loser. Read, reconcile, and save with the new revision; do not blindly overwrite.
- Values must be a JSON object, at most 64 KiB encoded, with nesting bounded to 20 levels. Prototype-related keys are rejected. Up to 32 package namespaces can be stored per desktop.
- Successful replacement returns a new opaque revision. Saving `{}` clears values but retains the namespace; v1 has no namespace deletion operation.
- A package migrates its own `schemaVersion` after reading, then saves using the same compare-and-replace rule. The server stores JSON and does not run package migration code.
- Preferences are an optional additive `desktop.packagePreferences` field. Ordinary desktop setting changes preserve them. Backups include them; old backups without the field are accepted. Restoring a backup replaces package preferences and assigns new revisions, preventing writes based on pre-restore state. Restoring an old backup clears package preferences.

## Verification

`src/protocol/v1/contract.test.ts` checks compatibility inventory, SDK import boundaries, errors, package metadata, and transport behavior. `src/lib/protocol-server/router.test.ts` verifies request rejection before dispatch. `e2e/protocol.spec.ts` connects the independent SDK to an isolated real HTTP server and verifies conflicts, backup round-trips, legacy clients, and the mismatch screen. The existing desktop browser suite exercises the built-in UI against `/api/v1`.

The source export includes non-ignored new files within its explicit product allowlist and still runs the private-content scan. This prevents a locally working SDK from disappearing from the public source snapshot before files are committed.
